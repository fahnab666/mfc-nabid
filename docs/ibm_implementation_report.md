# Immersed Boundary Method (IBM) Implementation Report

## Scope

This report describes the IBM implementation in MFC, focusing on:

1. how ghost cells/ghost points are identified and populated;
2. how immersed-body force and torque are computed with the fourth-order finite-difference option; and
3. how immersed-body collisions are detected and applied.

Primary implementation files are `src/simulation/m_ibm.fpp`, `src/common/m_finite_differences.fpp`, and `src/simulation/m_collisions.fpp`.

## 1. Overall execution sequence

IBM setup is performed in `s_ibm_setup()`:

1. The immersed-body marker field is cleared and repopulated from the configured IB geometry.
2. Ghost points are counted and stored in `ghost_points`.
3. A level set and its normal are computed for each ghost point.
4. The image point is placed inside the fluid, on the opposite side of the immersed surface from the ghost point.
5. Interpolation weights for the image point are calculated.
6. During the time-stepping loop, `s_ibm_correct_state()` interpolates the image-point fluid state and writes the corresponding state into the solid-side ghost cell.
7. For moving bodies, `s_compute_ib_forces()` integrates pressure and viscous contributions, adds collision contributions, communicates partial sums across MPI neighbors, and stores the resulting force/torque on `patch_ib(:)`.

The main call sites are in `src/simulation/m_time_steppers.fpp` and AMR-specific calls are in `src/simulation/m_amr.fpp`.

## 2. Ghost-point identification and population

### 2.1 Marker field

`ib_markers%sf(i,j,k)` is zero in fluid cells and nonzero in cells covered by an immersed body. The nonzero value encodes the IB patch ID and periodic-image information. The marker field is generated by `s_apply_ib_patches()` during IBM setup and is regenerated when a moving IB changes position.

### 2.2 Which solid cells become ghost points?

`s_find_ghost_points()` scans the computational cells. A marked cell is classified as a ghost point if at least one cell in a neighborhood extending `gp_layers` cells in each active direction has a zero marker. In 2-D, the z-neighborhood is disabled; in 3-D it is active. The default number of layers is defined as `gp_layers = 3` in `src/common/m_constants.fpp`.

For every detected point, the code stores:

- the grid index `loc`;
- the local IB patch ID;
- periodic image offsets in x/y/z;
- whether the patch uses slip or no-slip behavior; and
- `DB`, which records whether the point lies near a physical subdomain boundary.

On AMR runs, the GPU-created list is sorted lexicographically by `(i,j,k)` to make the downstream force reduction deterministic. Non-AMR runs retain the original list order.

### 2.3 Image-point location

For a ghost point at physical location `x_g`, the level-set distance is `abs(gp%levelset)` and the outward normal is `gp%levelset_norm`. The image point is placed using

```text
x_IP = x_g + 2 |levelset| n
```

This mirrors the point across the immersed surface. `s_compute_image_points()` then searches in each coordinate direction for the two neighboring cell centers bracketing the image point. If the image point is near a cell center, that cell receives unit interpolation weight. If an image point cannot be located within the available buffered domain, the code aborts with a diagnostic indicating that the ghost/image point crossed processor or buffer bounds.

### 2.4 Interpolation stencil and weights

`s_compute_interpolation_coeffs()` uses a 2x2 stencil in 2-D or a 2x2x2 stencil in 3-D. The nominal weight is inverse-square distance:

```text
eta_a = 1 / distance(x_a, x_IP)^2
```

Cells marked as solid are assigned zero admissibility factor `alpha_a`; fluid cells have `alpha_a = 1`. The normalized weight is

```text
w_a = alpha_a eta_a / sum_b(alpha_b eta_b).
```

If all candidate cells are marked solid, the fallback uses the normalized inverse-square weights without the solid-cell mask. This guarantees a usable interpolation stencil, although it indicates a locally constrained geometry.

`s_interpolate_image_point()` applies these weights to pressure, velocity, partial densities, volume fractions, color function, species, bubble variables, and other enabled model variables.

### 2.5 State written into a ghost cell

The image-point primitive state is used to reconstruct a thermodynamically consistent ghost state:

- partial densities and volume fractions are copied from the interpolated image state;
- pressure is copied from the image state, with an additional acceleration correction for `moving_ibm > 1`;
- momentum is reconstructed from `rho * vel_g`;
- total energy is rebuilt from the equation of state plus kinetic energy;
- reacting cases rebuild energy with the mixture thermochemistry rather than the ideal-gas closure;
- bubble/QBMM variables are interpolated and written back in their conservative representation.

The ghost velocity depends on the boundary type:

- **Slip:** the image velocity's normal component is removed, then the normal component of the body velocity is imposed. For moving bodies, rotational velocity `omega x r` is included.
- **No-slip:** a stationary body uses zero ghost velocity; a moving body uses translational plus rotational surface velocity.
- **Blowing/injecting surface:** an outward normal blowing velocity is added. If configured, it is pressure-scaled by a power law.

For moving bodies, cells that change from solid to fluid are repopulated from established fluid neighbors using inverse-distance averaging. This prevents a newly exposed fluid cell from retaining the low-pressure solid seed state.

## 3. Force and torque calculation

### 3.1 What is integrated

`s_compute_ib_forces()` performs a volume integration over all cells whose marker identifies an IB patch. The local force density is the pressure contribution plus, when `viscous = .true.`, the divergence of the viscous stress tensor:

```text
f = -grad(p) + div(tau)
```

The per-cell contribution is multiplied by cell volume. Torque is computed about the IB centroid:

```text
dT = r x f dV
```

where `r` is the cell-center position relative to the appropriate periodic image of the body centroid.

### 3.2 Finite-difference coefficients

The coefficients are generated by `s_compute_finite_difference_coefficients()` and stored in `fd_coeff_x`, `fd_coeff_y`, and `fd_coeff_z`. The arrays are coordinate-aware, so the implementation also supports nonuniform cell-center spacing.

For fourth-order centered first derivatives, the code sets coefficients for offsets `-2, -1, 0, +1, +2`:

```text
c_-2 =  1 / D
c_-1 = -8 c_-2
c_0  =  0
c_+1 = -c_-1
c_+2 = -c_-2

D = x_(i-2) - 8 x_(i-1) - x_(i+2) + 8 x_(i+1)
```

Therefore, for a scalar field `q`, the derivative at cell `i` is evaluated as

```text
q_s(i) = sum(r=-2,+2) c_r(i) q(i+r).
```

On a uniform grid, this is the familiar

```text
q_s(i) = [-q(i+2) + 8q(i+1) - 8q(i-1) + q(i-2)] / (12 ds).
```

The IBM force kernel uses the same coefficient arrays for the pressure gradient and for each directional divergence contribution of the viscous stress tensor. In 2-D it applies x and y derivatives; in 3-D it also applies the z derivative.

### 3.3 Pressure part

For every marked cell, the kernel accumulates

```text
f_pressure,x = - sum_r fd_coeff_x(r,i) p(i+r,j,k)
f_pressure,y = - sum_r fd_coeff_y(r,j) p(i,j+r,k)
f_pressure,z = - sum_r fd_coeff_z(r,k) p(i,j,k+r)
```

The fourth-order path is selected when `fd_order` is set to 4, which gives `fd_number = max(1, fd_order/2) = 2`. The ghost/buffer width must therefore be large enough to provide the ±2 stencil values.

### 3.4 Viscous part

The code computes a local dynamic viscosity as the volume-fraction-weighted mixture value:

```text
mu_local = sum_s alpha_s * (1 / Re_s).
```

For each stencil offset, `s_compute_viscous_stress_tensor()` is evaluated at the corresponding x-, y-, or z-shifted location. The directional stress rows are differentiated and added to the local force:

```text
f_viscous = d(tau_x,:)/dx + d(tau_y,:)/dy + d(tau_z,:)/dz.
```

The force and torque arrays are updated atomically because many grid-cell threads can contribute to the same body.

### 3.5 Post-processing of force

After fluid pressure/viscous integration, the routine:

1. adds IBM collision forces and torques;
2. communicates partial body sums between neighboring MPI ranks;
3. adds configured body-force contributions `mass * acceleration`; and
4. writes the totals to `patch_ib(i)%force` and `patch_ib(i)%torque`.

### 3.6 Important benchmark setting

The supplied `benchmarks/ibm/case.py` sets:

```python
"fd_order": 2,
```

Thus the benchmark currently exercises the second-order centered derivative, not the fourth-order option. To exercise the fourth-order IBM force path, set `fd_order` to `4` and ensure the configured buffer/stencil extent is compatible with the ±2 accesses.

## 4. Collision implementation

### 4.1 Activation and model

Collision handling is called from `s_compute_ib_forces()` through `s_apply_collision_forces()`. It returns immediately when `collision_model == 0`. The implemented selectable model in this routine is `collision_model == 1`, a soft-sphere model.

At initialization:

```text
eta_0 = -2 log(e) / collision_time
k_0   = (pi^2 + log(e)^2) / collision_time^2
```

Here `e` is the coefficient of restitution. For a pair of bodies, the effective mass scales these constants:

```text
m_eff = 1 / (1/m_1 + 1/m_2)
k     = k_0 m_eff
eta   = eta_0 m_eff.
```

### 4.2 IB-to-IB collision detection

`s_detect_ib_collisions()` uses ghost-point locations as an inexpensive narrow-phase candidate source. Around each ghost point it searches a 5x5x(1 or 5) marker neighborhood for a marker belonging to another IB. Candidate pairs are decoded from periodic marker IDs, self-periodic collisions are removed, and duplicate pairs are coalesced in `collision_lookup`.

The final geometric test uses the periodic-image centroids:

```text
overlap = radius_1 + radius_2 - |x_2 - x_1|.
```

A collision is applied only when `overlap > 0` and the current MPI rank owns the collision location.

### 4.3 IB-to-IB force law

The unit normal is

```text
n = (x_2 - x_1) / |x_2 - x_1|.
```

The contact-point velocities include translation and rotation:

```text
v_1 = U_1 + omega_1 x r_1
v_2 = U_2 + omega_2 x r_2.
```

The relative velocity is decomposed into normal and tangential parts. The normal force is

```text
F_n = -k overlap n - eta v_rel,n.
```

The tangential friction force is

```text
F_t = -mu |F_n| t_hat,
```

where `mu = ib_coefficient_of_friction`. The total contact force is `F_n + F_t`. The tangential force generates torque through `r x F_t`. Equal and opposite forces are applied to the two bodies, and the updates use atomics.

### 4.4 IB-to-domain-wall collision

`s_detect_wall_collisions()` checks each IB against physical domain faces that use slip-wall or no-slip-wall boundary conditions. It stores the body overlap with each face in `wall_overlap_distances`.

The wall force uses the same soft-sphere structure, but the effective mass is the body mass:

```text
k   = k_0 mass
eta = eta_0 mass.
```

The wall normal is selected from the impacted domain face. Translational and rotational body velocity are evaluated at the contact location, then normal damping, elastic repulsion, tangential friction, and torque are added to the body force/torque arrays.

## 5. Practical verification checklist

- Confirm `ib = .true.` and that `num_ibs` and `patch_ib(:)` are configured.
- Confirm `fd_order = 4` when fourth-order IBM force evaluation is intended; the shipped IBM benchmark uses 2.
- Confirm the buffer width covers the finite-difference half-stencil and the image-point search.
- Check that `viscous = .true.` is intentional; otherwise only pressure-gradient force is integrated.
- For collisions, set `collision_model = 1`, choose a physically meaningful `collision_time`, `coefficient_of_restitution`, and friction coefficient, and verify body masses are positive.
- For MPI runs, confirm body centroid ownership and force communication are not being mistaken for duplicate force contributions.
- For moving IBs, verify that force computation occurs before the body update and that freshly uncovered cells are repopulated.

## 6. Moving IBM on a tiled L1 AMR region

For a large L1 region on multiple MPI ranks, set a positive `amr_max_grid_size`. The AMR initializer then tiles the region into
rank-sized fine blocks. Moving-IBM rebuild and correction are applied only on tiles whose buffered body bounding box intersects the
tile; unrelated fluid tiles are left untouched. The existing contiguous-body behavior is preserved when `amr_max_grid_size = 0`.

The fine-IBM stencil is intentionally fail-closed: every moving body and its image-point support must remain within one tile. Align
the L1 box and tile size accordingly. The validated 2-D example
`examples/2D_particle_bed_amr_8cpu_force_loaded/case_4x_area_amr_domain.py` uses:

```python
"amr_block_beg(1)": 80, "amr_block_end(1)": 175,
"amr_block_beg(2)": 80, "amr_block_end(2)": 175,
"amr_max_grid_size": 32,
```

The `[80:175]` box is four times the original 32-cell refined area. Its central 32-cell tile contains the four-particle bed and its
trajectory. The case completed 80 steps on 8 CPU MPI ranks without NaNs or containment aborts. Run it with:

```text
./mfc.sh run examples/2D_particle_bed_amr_8cpu_force_loaded/case_4x_area_amr_domain.py --no-gpu -n 8 -j 8 -t pre_process simulation
```

GPU execution still requires validation with the target Cray compiler and accelerator runtime; the local macOS gfortran does not
provide AMDGCN offload support.
